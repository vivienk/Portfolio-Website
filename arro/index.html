SCREEN 02 · IDEA QUESTIONS

Before I started coding

01

Who is the user?

Researchers needed to change studies without rebuilding the flow. Participants needed one coherent session—not a prototype, questionnaire, and recording tool stitched together.

02

Why was it worth building?

The sequence around an answer was part of the research data: what someone saw, what they did, and what they thought at that moment.

03

What was the MVP?

Connect a prototype, arrange tasks and questions, publish one URL, record consented behavior, and reuse the system for the next study.

The goal was not to rebuild Maze. It was to remove the recurring friction in our research loop.

SCREEN 03 · PLAN CHECKLIST

Before I started building

01

Features

Prototype tasks, open questions, five-point scales, instruction screens, drag-reordered flows, multiple studies, preview, and publishing.

02

Architecture

Separate the person defining the experiment from the person completing it, with a reusable configuration layer between them.

03

Data model

Keep prototype code, research configuration, and participant responses independent so each can evolve safely.

SCREEN 04 · TECH STACK + BUILD

Choosing the smallest stack that could support the loop

Structured configuration turned “build another testing page” into “configure another study.” The tool became a small internal CMS for user research.

Interface

Configuration + responses

Iteration

Vercel

SCREEN 05 · AI VERIFY CHECKLIST

Before pushing to production

Cheaper code generation made product-level verification more important.

01

Run tests

Can participants complete the flow, and can every step type coexist?

02

Run build

Verify the production build—not just the local prototype.

03

Check errors

Malformed input, missing configuration, failed APIs, authentication, and payload limits.

04

Check links

Admin → config → prototype → participant → recording.

05

Self-review + fix

Test as both researcher and participant; component success does not prove workflow success.

SCREEN 06 · OUTCOME

I turned a recurring workflow into infrastructure.

The team could structure research around the product experience: connect live prototypes, ask questions closer to the interaction, observe behavior and explanation together, and reuse the same system across testing projects.

01

Research in context

Behavior, prompts, and qualitative responses stay inside one participant flow.

02

Reusable by design

Study structure is data, so new tests do not require a new frontend.

03

Owned end to end

I moved from workflow definition through system architecture, implementation, instrumentation, and QA.

WHAT I LEARNED

AI lowers the cost of implementation. It raises the value of product judgment.

The highest-leverage work was deciding what should exist, what should wait, how the pieces should connect, and how to know the system actually worked.
